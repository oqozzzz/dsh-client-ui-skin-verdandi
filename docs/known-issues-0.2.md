> 记录 0.2.0-rc.2 桌面端适配中已识别、尚未修复的问题。每条含现象、根因分析与修复方向。
> 现象均以 2026-10-07 的实测截图为准（4 张侧边栏相关截图见 issue #1）。

## #1 右侧栏分栏「开始」页面无皮肤（官方白底）

**状态**：未修复 · **优先级**：中（纯视觉不一致，无功能影响）

### 现象

右侧栏（右侧边栏）拆分出的「开始」页面为官方白色原版 UI，与两侧已换肤表面形成强烈反差：

- 截图 1：右侧栏单栏「开始」页（工作区文件 / 新建终端 / 浏览器 三张白色卡片），左侧栏与会话区皮肤正常
- 截图 2 / 3：右侧栏拆成**双栏**，两个「开始」页均为白底
- 截图 4：窄窗口下右栏仍为白底

注意：左侧边栏在这些截图中均正常（深红 + 装饰完整），"没有皮肤"的只有右侧栏的面板页。

### 根因分析

1. **这些页面属于 0.2 新增的右侧栏面板体系**。0.2 的右侧栏（`sidebar-right` 插件）不只有
   事件详情视图，还能拆分成多栏（layout 层的 `data-rightbar-col` / `data-rightbar-collapsed`），
   每栏可承载「开始」启动页（工作区文件 / 新建终端 / 浏览器 快捷卡片）或终端 / 浏览器 /
   文件浏览等工具面板。这一整套是 0.1 没有的新表面，皮肤的着色清单从未覆盖它。

2. **皮肤的着色范围缺口**。当前打标体系只覆盖四类表面：
   - 左栏：`[data-verdandi-pane='sidebar']`（深红 + 装饰）
   - 聊天：`[data-verdandi-pane='conversation']`（场景背景 + 舞台，含 overflow 裁剪）
   - main 槽非聊天面板：`[data-verdandi-panel]`（场景背景，无裁剪）——插件管理页 / 自动化任务页走这条
   - details：`[data-verdandi-pane='details']`

   右侧栏的结构是 `[data-slot='rightbar']`（display:contents 包装）→ `OUqwTW_session` →
   `rightbar.session`（contents）→ `OUqwTW_panel`（真实盒），与 main 槽的
   "contents 包装 + 真实盒租户"完全同构，但 `resolveConversationPane` 只探测
   `main` 槽，**rightbar 槽内的面板租户从未被打上 `data-verdandi-panel`**，因此没有背景。

3. **即使补了背景，「开始」卡片本身仍是白色自绘表面**。三张卡片是宿主用自己的
   `--dsw` token 画的白色圆角卡，白卡叠在场景背景上本身协调，但卡片之外的面板底色
   若直接透出场景插画，卡片与插画之间的对比关系需要重新调纱幕浓度（参考
   `[data-verdandi-panel]` 用过的加重纱幕方案）。

### 影响面

- 单栏、双栏、窄窗口三种形态全部受影响（即右侧栏的所有「开始」页）
- 终端 / 浏览器 / 文件浏览等已打开的工具面板是否同样白底待复现确认（推测同样受影响，
  它们挂在同一条 rightbar 面板链上）

### 修复方向（建议，未实施）

1. `decoratePanes` 增加右侧栏租户解析：从 `[data-slot='rightbar']` 下沉到真实盒
   （复用 `display: contents` 下降逻辑），打上 `data-verdandi-panel`（或单独的
   `data-verdandi-panel='rightbar'` 变体），复用现有场景背景 + 纱幕规则
2. 分栏数量可变（1–4 栏），每栏面板都要打标——建议按 `rightbar.session` 之后的每根
   真实盒逐个处理，而不是只处理第一个
3. 「开始」卡片的白底如需跟随换肤，需把卡片容器映射到皮肤纸面 token
   （`--dsw-specific-bubble` 族），单靠面板背景不够
4. 右栏工具面板（终端 xterm 等）打背景时注意延续现有约定：不碰 xterm 调色板

## #2 会话末行文字被输入卡顶部的「誓约之戒·书册」装饰遮挡

**状态**：未修复 · **优先级**：中（长会话末行遮挡，影响阅读最后一条回复的收尾内容）

### 现象

会话最后一条消息文字较多、滚动到底部时，**最后一行文字的水平居中区域**被输入卡顶部的
「誓约之戒·书册」装饰压住。同时该行还可能被输入卡自身的不透明卡体与深红顶边框裁切——
截图中文字上贯穿的红色横线即输入卡顶边。

### 实测几何（0.2.0-rc.2 桌面端）

| 元素 | 位置（视口坐标） | 备注 |
|------|------------------|------|
| `composer-seal` 装饰 | x 812–916，**y 631–699**，z-index **5** | 比输入卡上缘凸出约 48px，水平居中，宽约 104px |
| 输入卡（`data-composer-card`） | y 679–791 | 不透明卡体 + 顶边框 |
| 会话流文字层 | z-index 低于装饰 | 滚动区底部可到达 y≈679（输入卡上缘） |

### 根因分析

1. **装饰按设计凸出输入卡上缘**（挂章式审美：书册桥接会话流与输入卡），`composer-seal`
   的 z-index（5）高于会话流文字层——文字滚动到装饰所在的 48px 条带就被绘制在装饰之下。
2. **0.2 的会话滚动容器把输入卡作为 overlay 覆盖在滚动内容上**
   （`scrollBody:has([data-conversation-composer-overlay])`），滚动到底时最后一行文字可以
   一直滚到输入卡上缘所在的高度；0.1 上是否有同样的覆盖关系、还是滚动区底部有额外预留，
   **待在 0.1 环境对照确认**（若 0.1 同样存在，则属于皮肤一直以来的布局取舍在 0.2 长文
   场景下显形）。
3. 皮肤的可读性 slip 体系只给特定行加纸面承托，没有为「滚动区底部边缘 + 装饰凸出带」
   这一条状区域留白。

### 影响面

- 长文末行在水平居中约 104px 宽的区间内被遮挡；紧贴输入卡的行会被卡体裁切（整行宽度）
- 左右两侧不受影响（装饰居中）

### 修复方向（建议，未实施）

1. **方案 A（推荐）**：把 `composer-seal` 的 z-index 降到会话流文字层之下——文字绘制在
   装饰上方，无文字处装饰照常显示。层级语义更合理（正文 > 装饰），改动一行。
   需实测装饰与输入卡边框的叠加关系是否仍然美观。
2. 方案 B：给会话滚动内容的底部加 padding（约等于装饰凸出高度 48px），让最后一行能
   滚出装饰带。需要在 0.2 滚动容器上找稳定锚点（宿主 hash 类
   `scrollBody:has([data-conversation-composer-overlay])` 的容器），运行时验证。
3. 方案 C：缩小装饰的凸出高度（设计变更，不作为首选）。
4. 卡体裁切部分是宿主 overlay 布局的原生行为；若也要解决，等价于要求宿主滚动区为
   overlay 输入卡预留 padding——可先只在皮肤侧做方案 A。

## #3 会话滚动条：滚轮悬停滚动变 0 帧瞬跳；滑块行程与右缘头像/标记元素重叠

**状态**：未修复 · **定性**：疑似宿主行为（皮肤零参与），待关皮肤对照确认

### 现象

会话区右缘有一条**细长白色竖条**（红圈元素）：

1. 鼠标悬停在白条上使用滚轮时，滚动的平滑动画失效，变为 **0 帧瞬跳**（内容直接跳到
   目标位置，无过渡）
2. 白条（滑块）的行程位置可能与**头像元素**发生视觉冲突（截图 1：圆形头像徽章恰好
   压在白条上端；头像为白色相框 + 红色缎带的誓约头像样式）

白条特性：鼠标按住可上下拖动（典型滚动条滑块行为），松开后停在原处。

### 白条身份（已确认）

`Dc7zOa_scrollBody`（0.2 会话滚动容器）的 **webkit 自定义滚动条**，宿主样式：

- 轨道宽 **5px**、背景透明，滑块背景 `rgb(229, 229, 229)`（浅白灰）——即"白色条"
- 轨道沿滚动容器右缘全程分布（容器 1173×732，scrollH 5439）
- **皮肤零参与**：`verdandi.module.css` 中没有任何 `::-webkit-scrollbar`、
  `scroll-behavior` 或 smooth 相关规则；白条在关皮肤后依然存在（同一样式）

### 根因分析

1. **0 帧瞬跳**：滚轮事件落在滚动条上时，浏览器把滚动直接交给滚动容器原生处理。
   若宿主对滚轮实现了 JS 平滑滚动动画（内容区滚轮的常规表现是平滑的），滚动条路径
   会绕过该动画，表现为瞬时跳变。**推测为宿主行为**：皮肤未触碰任何滚动机制；
   待做一次"关皮肤对照"——若关皮肤后滚轮悬停滚动条仍瞬跳，即可定性上游并反馈。
2. **滑块与头像/标记重叠**：右缘同一条 5px 轨道区间上还叠着 0.2 的**轮次导航迷你地图**
   （`xpvNua_marks` / `_markActive` 刻度，28px 宽，右缘 y≈382 起），滑块全程行程
   （0 → scrollH）必然多次穿过该区域——刻度、滑块、以及附近任何悬浮头像徽章
   （截图 1 中箭头所指的圆框头像）在窄轨道上互相叠压。属宿主把多个右缘悬浮件
   布局在同一纵向通道导致的拥挤，皮肤未参与定位。

### 影响面

- 滚轮悬停滚动条时每次滚动都是硬切，长会话下观感突兀
- 滑块行程与右缘悬浮件（迷你地图刻度 / 头像徽章）重叠，视觉拥挤
- 左侧人物立绘不受影响（滚动条在右缘；截图裁切造成的"在左侧"为错觉）

### 修复方向（建议，未实施）

1. 先做**关皮肤对照实验**定性：瞬跳与重叠若在无皮肤时依旧 → 上游问题，建议向
   DeepSeek Harness 反馈（附本节几何数据）；皮肤侧可考虑跟随上游修复，不单独 patch
2. 皮肤侧可做的缓解（可选）：给会话滚动条做皮肤化样式（更细 / 半透明 / 悬停渐显），
   降低与右缘悬浮件的视觉冲突——属于美化而非修复行为差异
3. 若确认宿主有 JS 平滑滚动动画：检查动画取消条件是否过于宽泛（任何 pointer 事件
   即取消），属宿主逻辑问题

## #4 滚动到底部的会话文字从输入卡下方条带透出（皮肤回归）

**状态**：未修复 · **定性**：**皮肤回归**（A/B 实测确认，非宿主行为）

### 现象

会话内容较长、滚动到底部时，**输入卡下缘与面板底边之间的条带**会透出滚过去的
会话文字（截图中输入卡下方的"行为变更，故 CHANG…"一行）。官方桌面端同位置干净。

### 实测几何（0.2.0-rc.2 桌面端，开/关皮肤 A/B）

| 度量 | 皮肤开 | 官方（关皮肤） |
|------|--------|----------------|
| 输入卡（`data-composer-card`）高度 | **112px**（679–791） | **158px**（660–818） |
| 卡体下缘 → 面板底边的暴露带 | **57px**（791–848） | **30px**（818–848） |
| 滚动容器（`scrollBody`）覆盖 | 116–848（全高，输入卡是 overlay） | 同左 |
| 滚动内容 padding-bottom | 0 | 0 |

### 根因分析

1. **0.2 的会话滚动区把输入卡作为 overlay 覆盖在滚动内容上**（
   `scrollBody:has([data-conversation-composer-overlay])`），`scrollBody` 贯穿面板全高、
   滚动内容无底部预留——文字可以一直滚到面板底边，途经输入卡"背后"。
2. **官方靠更高的卡体遮住大半**：官方卡体 158px，只有最底部 30px 条带暴露；且官方
   用量统计行画在卡体/seat 流内，进一步压缩透出区间。
3. **皮肤把这套几何压紧了**：`[data-composer-card] { min-height: 112px }` + dock 药丸化
   （紧凑统计条 `margin: 3px auto 0`）让卡体矮了 46px，暴露带从 30px 扩大到 57px；
   同时皮肤把宿主相关表面改成了透明（场景背景方案），该条带不再有不透明的官方白色
   底板可以遮字——两层因素叠加，滚过的文字直接透出。

### 影响面

- 长会话滚到底时，输入卡下方的 57px 条带持续透出滚动文字，观感差
- 左右两侧不受影响；深色模式下同样存在（背景更暗，文字透出同样明显）

### 修复方向（建议，未实施）

1. **方案 A（推荐）**：给 `[data-composer-seat]`（或 composer dock 的底部区域）补一块
   不透明的皮肤纸面背景（veil/纸色），覆盖卡体下缘到面板底边的条带——把"透出"改回
   "遮住"，不改紧凑化设计。注意与 `composer-veil-inner` / 蕾丝装饰的叠加关系。
2. 方案 B：放宽输入卡紧凑化（恢复接近官方的卡体高度），暴露带回落到官方的 30px——
   但仍非零，治标。
3. 方案 C：给滚动内容加 `padding-bottom`（约 seat 高度），让文字根本不进入卡后区域——
   需要宿主滚动内容的稳定锚点，且会改变滚动条比例。

## #6 左侧栏偶发整块内容不渲染（只剩深红背景与边框装饰）

**状态**：未定性 · **优先级**：中（偶发，复现条件未锁定）

### 现象（截图 1）

左侧栏整块只有深红背景、`::before` 边框与 veil 角饰，**品牌行、新会话按钮、
插件/自动化任务导航、工作区列表全部不显示**——即宿主侧栏内容整体未绘制。

同组另一张截图（截图 2）显示当时屏幕上叠着 **`aether-story-studio-next` 插件详情
浮层**（含 今日消费 / 余额 / 更新于 等结算信息），推断两者为同一时刻：
**某个插件详情/结算浮层打开期间，左侧栏内容未绘制**。

### 已排除（当前状态实测）

在浮层关闭后的正常状态下实测，侧栏 **DOM 内容完整且几何正常**：

- 22 个按钮、文字齐全（新会话 / 插件 / 自动化任务 / 工作区列表）
- 5 个宿主内容块（logoRow 40px、newSession 42px、panelList 91px、regionArea 543px、
  footArea 52px）display/visibility/opacity 全部正常
- 面板标记、`isolation: isolate`、`position: relative` 均在

即：**不是内容被删除，而是特定瞬态下的绘制/层叠问题**。

### 嫌疑排序（未证实）

1. **宿主插件详情浮层打开时，侧栏宿主组件被虚拟化/卸载**（浮层全屏接管期间侧栏
   内容不渲染是宿主的正常省电行为？）——若如此，皮肤只是如实画了空侧栏的背景与
   装饰，行为与官方一致，不算皮肤 bug；需要复现时检查侧栏 DOM 是否为空
2. **皮肤装饰层叠条件性遮挡**：浮层打开会置 `body[data-verdandi-modal-open]`，触发
   侧栏 `::before/::after`（边框与蕾丝）opacity 0——但这些只是装饰，不遮内容；且
   实测内容层与装饰层 z 序正常（内容 0 / portrait -1 / tree -2 / 边框 4 / 角饰 7），
   全块内容同时被遮需要一块全尺寸不透明层，当前不存在
3. **`isolation: isolate` + 浮层层叠的交互**：低概率，未发现具体路径

### 复现时需捕获（下次出现立即抓）

1. 侧栏 `outerHTML` 长度 + 子元素数（判断宿主内容是否还在 DOM）
2. `[data-verdandi-pane='sidebar']` 的 computed `display/visibility/opacity/overflow`
   与第一个内容子块的同项数据
3. 当时打开的浮层/对话框清单（`[role='dialog']`、shell.overlay 子节点、body 的
   `data-verdandi-modal-open`）
4. 一张同步截图

### 修复方向

- 若确认浮层期间宿主侧栏内容被卸载：皮肤侧无行为差异，属宿主表现，建议上游反馈；
  皮肤可评估浮层期间是否暂停侧栏装饰绘制（省一块空背景的违和感）
- 若复现时 DOM 内容仍在但不绘制：按捕获数据定位层叠/裁切路径后修
